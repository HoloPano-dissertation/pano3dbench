# Методы и как их запускать

Три метода статьи — **DPC**, **Im3D-Pano** и **Total3D-Pano** — это **конфигурации одной
программной базы DeepPanoContext**, а не три отдельных репозитория. У них общие детектор
(detectron2), оценка макета (HorizonNet) и оценка трёхмерных рамок (BEN). Различаются они
головой формы и оптимизацией отношений на Scene-GCN. Поэтому все три пишут одинаковый
`data.pkl`, один конвертер `dpc_runner.convert_data_pkl` переводит его в `SceneOutput`,
и показатели считаются по одной методике.

| Метод            | Форма   | Оптимизация отношений                   | Как получен                                     |
|------------------|---------|-----------------------------------------|-------------------------------------------------|
| **DPC**          | LDIF    | включена                                | вывод на весах авторов                          |
| **Im3D-Pano**    | LDIF    | **выключена** (`relation_adjust False`) | абляция DPC и голова LDIF, обученная с нуля     |
| **Total3D-Pano** | **MGN** | выключена                               | голова MGN в коде DeepPanoContext, обучена нами |

Команды для каждой строки — в [igibson.md](igibson.md) и [front3d.md](front3d.md).

## Проверка ядра без GPU

**fixture** — самая быстрая проверка пути «конфигурация → набор → показатели → отчёт»
по готовым предсказаниям из папки, без окружения и без подпроцесса:

```bash
pano3dbench run --config configs/demo/smoke.json
```

**echo** — весь путь «менеджер окружений → раннер в подпроцессе → показатели» на пустом
venv: раннер возвращает одну и ту же сцену. Если ломается DPC, echo показывает, где
искать ошибку: в окружении модели или в ядре.

```bash
pano3dbench env prepare --env configs/environments/echo.yaml
pano3dbench run --config configs/demo/echo_local.yaml
```

## Три метода подробнее

**DPC** — полный метод: голова LDIF, оптимизация отношений включена, веса авторов.
**Im3D-Pano** — тот же код и те же веса с выключенной оптимизацией отношений
(`--model.scene_gcn.relation_adjust False`). Сохранённый вывод DPC сделан с включённой
оптимизацией, поэтому этой строке нужен свой запуск вывода в свою папку.
**Total3D-Pano** — общий ствол с головой MGN вместо LDIF и без Scene-GCN; MGN есть в коде
DeepPanoContext, обучен нами.

### Отладка конвертера без вывода

Если `data.pkl` уже есть, раннер переведёт только его:

```bash
conda run -n Pano3D python runners/dpc_runner.py \
  --request <request.json> --output <out.json> \
  --data-pkl path/to/out/pano3d/<run>/visualization/<scene>/data.pkl
```

### На что ушло время

- DPC нужен старый стек (torch 1.7.1+cu110, Python 3.7); `configs/environments/dpc.yaml`
  снимает жёсткие версии авторов. Правки исходников применяет `scripts/dpc/dpc_postsetup.py`,
  повторный запуск ничего не ломает.
- Системные пакеты (`xvfb`, `ninja-build` и др.) не ставятся автоматически, нужен
  администратор. Их список выводит `env prepare --dry-run`.
- Префикс `.module.` в ключах весов **убирать нельзя**: модель оборачивает подсети
  в `DataParallel` и ждёт его. Без префикса веса BEN, формы и макета молча не загружаются,
  и рамки получаются мусорными.
- Опорные сети torchvision объявлены в спецификации как веса, поэтому их кладут заранее,
  а не скачивают при первом проходе. Это важно на узле без сети.

## Выбор конфигурации

У каждого метода две конфигурации — два пути к одной методике, а не две методики:
`<метод>_rescore.yaml` считает предсказания, уже переведённые в JSON (`model.type: fixture`,
без окружения модели), `<метод>.yaml` запускает саму модель через менеджер окружений
(`model.type: dpc`). Оба пути дают одинаковые числа на всех 500 сценах iGibson.

| Цель                                   | Команда                                                        |
|----------------------------------------|----------------------------------------------------------------|
| проверить ядро за секунды              | `run --config configs/demo/smoke.json`                         |
| проверить менеджер окружений локально  | `run --config configs/demo/echo_local.yaml`                    |
| строка метода по готовым предсказаниям | `run --config configs/igibson/runs/<метод>_rescore.yaml`       |
| строка метода через окружение          | `run --config configs/igibson/runs/<метод>.yaml`               |
| вывод DPC с нуля                       | см. [igibson.md](igibson.md#уровень-3-вывод-и-обучение-с-нуля) |

### Почему нет отдельного раннера на метод

Три метода — конфигурации одной программной базы и пишут одинаковый `data.pkl`, поэтому
у них одна спецификация окружения и один раннер (`runners/dpc_runner.py`). Метод выбирается
аргументами из конфигурации эксперимента:

```yaml
model:
  type: dpc
  parameters:
    environment: ../../environments/dpc.yaml
    runner_args: [ "--pred-root", "out/pano3d_im3d", "--model", "im3d-pano",
                   "--relation-adjust", "False" ]
```

`--pred-root` выбирает метод при подсчёте готового вывода: каждая конфигурация пишет
предсказания в свою папку (`out/pano3d` для DPC, `out/pano3d_im3d`, `out/pano3d_total3d`
и т. д.), поэтому предсказания двух методов не смешиваются в одной строке.
`--relation-adjust` и `--config` важны, только когда раннер сам запускает вывод.
Выбранные аргументы записываются в `run.json`, и по нему видно, какая конфигурация дала
строку.

Действительно другой метод, не конфигурация DPC, подключается своим раннером и своей
спецификацией окружения, ядро при этом не меняется. Минимальный пример —
`runners/echo_runner.py`, подробности — в [architecture.md](architecture.md#подключение-своей-модели).
